\begin{abstract}
EvoCracker is an AI-first dungeon game where enemies evolve to counter player behavior across repeated runs.
The project combines a PixiJS runtime, React overlays, custom search algorithms, behavior trees, and a genetic algorithm.
This report documents architecture, implementation decisions, hosting completion, measured outcomes, and engineering challenges.
It also captures practical coding nightmares and how those incidents shaped the final system.
\end{abstract}

\section{Introduction}

EvoCracker started as an attempt to build a dungeon game where AI behavior is not scripted once and left static.
The core idea was to let enemies adapt between rounds using telemetry from real player runs.
That required building three things together: a solid real-time game runtime, an observable AI stack, and a reproducible evolution loop.

The production deployment is available at \url{https://evocracker.vercel.app/} and the full source is in \url{https://github.com/AVM4D/EvoCracker}.
The implementation is organized across the phase documents in \texttt{docs/PHASE\_1\_...PHASE\_5} and finalized here with architecture details, severe failures, and release notes.

\section{System Architecture Overview}

EvoCracker follows a layered design where rendering, AI, gameplay systems, and analytics are decoupled but connected through clear contracts.

\subsection{Executive technical summary}
\begin{itemize}[leftmargin=6mm]
  \item \textbf{Runtime model}: Single-threaded render/game loop with async pathfinding requests and deterministic state snapshots.
  \item \textbf{AI model}: Three-layer stack (Behavior Tree orchestration, search-based navigation, GA adaptation).
  \item \textbf{Data model}: Centralized Zustand state with persisted run history and iteration proofs.
  \item \textbf{Ops model}: Static frontend hosting with Supabase-backed leaderboard and telemetry persistence.
\end{itemize}

\section{Game Brain: Technical Deep Dive}
\label{sec:brain}

\subsection{Search algorithms}
Eight algorithms are implemented from scratch and exposed through a strategy registry:
\begin{itemize}[leftmargin=6mm]
  \item Uninformed: BFS, DFS, IDS, DLS.
  \item Cost and heuristic-driven: UCS, A*, Greedy Best-First Search.
  \item Local optimization: Hill Climbing.
\end{itemize}

Every run returns path, nodes expanded, visited nodes, and compute time to power real-time analysis.

\subsection{Behavior trees}
Each enemy has a behavior tree with tactical branches for patrol, investigate, chase, and retreat behavior.
Blackboard state includes player visibility, last known coordinates, health state, and timers.

\subsection{Genetic algorithm}
At iteration boundaries, genomes are evaluated and evolved:
\[
f(g)=0.3\cdot visible + 2.0\cdot damage + 1.5\cdot detections + 0.2\cdot survival + 0.4\cdot coverage - 1.0\cdot stuck + 2.5\cdot coop
\]
Selection, crossover, and mutation produce the next population and proof records.

\subsection{Behavior-tree decision contract}
To make enemy behavior debuggable and comparable, each behavior cycle follows a strict contract:
\begin{enumerate}[leftmargin=6mm]
  \item \textbf{Sense}: Vision and proximity update blackboard fields.
  \item \textbf{Select}: BT chooses tactical branch (patrol/search/chase/flee).
  \item \textbf{Plan}: Branch requests path using assigned algorithm and current constraints.
  \item \textbf{Act}: Path follower advances, combat checks run, runtime metrics update.
  \item \textbf{Record}: Snapshot is emitted for analytics and evolution scoring.
\end{enumerate}

\subsection{Algorithm quality controls}
The implementation includes practical controls to keep comparisons fair:
\begin{itemize}[leftmargin=6mm]
  \item standardized output shape: path, expanded nodes, visited nodes, runtime, success flag;
  \item consistent Grid interface and tile-weight semantics across all algorithms;
  \item dashboard instrumentation from live enemies, not synthetic benchmark harnesses.
\end{itemize}

\subsection{Key architectural decisions}
\begin{itemize}[leftmargin=6mm]
  \item \textbf{Centralized store over ad-hoc local state}: selected to keep runtime telemetry, evolution history, and UI views coherent.
  \item \textbf{Registry-based algorithm dispatch}: selected to preserve algorithm modularity and simplify comparative instrumentation.
  \item \textbf{Behavior tree orchestration}: selected to keep tactical decisions interpretable and debuggable compared to opaque policy logic.
  \item \textbf{Iteration proof as first-class artifact}: selected so progress claims remain auditable and reproducible.
\end{itemize}

\section{Findings and Problems Faced}
\label{sec:findings}

\subsection{What worked well}
\begin{itemize}[leftmargin=6mm]
  \item Event-driven boundaries and centralized state made debugging practical.
  \item Algorithm Lab significantly reduced AI debugging time.
  \item Iteration proof records turned adaptation claims into measurable evidence.

\subsection{What was difficult}
\begin{itemize}[leftmargin=6mm]
  \item Balancing real-time game loops against React overlay reactivity.
  \item Preserving algorithm diversity without letting one strategy dominate.
  \item Supporting mixed art/map pipelines while keeping runtime stable.
\end{itemize}

\section{Coding Nightmares (Severe Incidents)}
\label{sec:nightmares}

\subsection{Nightmare 1: asset transparency corruption}
\textbf{What happened}: Early custom-generated assets repeatedly lost detail or developed color halos when backgrounds were removed.

\textbf{Fix}: Added deterministic background-removal logic in the sprite loading pipeline and safer fallback behavior.

\subsection{Nightmare 2: IDS, DLS, and Hill Climbing instability}
\textbf{What happened}: IDS, DLS, and Hill Climbing initially produced unstable movement under dynamic combat conditions.

\textbf{Fix}: Improved path refresh policy, fallback behavior, and analytics instrumentation for path progress and compute cost.

\subsection{Nightmare 3: alert-state freeze loops}
\textbf{What happened}: Alert/chasing oscillations could repeatedly trigger stun-style transitions, freezing movement in edge cases.

\textbf{Fix}: Added guarded transition logic and anti-loop conditions on alert-state changes.

\subsection{Nightmare 4: telemetry and state drift under high-frequency updates}
\textbf{What happened}: During high-action scenes, the runtime state and overlay snapshots could drift temporarily, causing misleading analytics cards and difficult triage.

\textbf{Fix}: Enforced tighter update cadence boundaries and clearer ownership of snapshot writes in the store pipeline.

\subsection{Nightmare 5: map and algorithm mapping mismatches across systems}
\textbf{What happened}: Character and enemy names diverged in enums/sprite definitions, breaking algorithm labels and analytics consistency.

\textbf{Fix}: Normalized naming across constants, sprite definitions, enemy factories, and analytics mappings.

\subsection{Nightmare 6: first-frame delta spikes and movement discontinuity}
\textbf{What happened}: Rare frame-time spikes caused sudden movement jumps and unstable physics/path behavior.

\textbf{Fix}: Added delta clamps and stabilized movement/path update cadence.

\subsection{Nightmare 7: initialization race during screen transitions}
\textbf{What happened}: Rapid screen transitions could overlap teardown and re-init logic, causing duplicate runtime objects or orphaned listeners.

\textbf{Fix}: Introduced stricter cleanup ownership and abort guards before reinitialization.

\subsection{Nightmare 8: stale path targets under rapid player direction changes}
\textbf{What happened}: Enemies occasionally pursued stale targets when player movement changed direction rapidly, producing visibly delayed reactions.

\textbf{Fix}: Reworked path-target invalidation and request gating to prefer current tactical context.

\subsection{Nightmare 9: ally behavior deadlock under shared enemy semantics}
\textbf{What happened}: Allies reused enemy runtime logic and inherited alert semantics that were incompatible with ally-follow behavior, causing lock states.

\textbf{Fix}: Separated ally alert handling and disabled hostile alert transitions in ally steering flow.

\subsection{Nightmare 10: tilemap mixed-source inconsistencies}
\textbf{What happened}: Legacy tileset assumptions and Tiled JSON data occasionally disagreed on gid/animation semantics, producing rendering anomalies.

\textbf{Fix}: Standardized gid normalization and added explicit tileset resolution fallback paths.

\subsection{Nightmare 11: analytics card duplication and mislabeling}
\textbf{What happened}: Genome and algorithm views could show repeated-looking cards due to incomplete mapping keys and name collisions.

\textbf{Fix}: Added stricter mapping keys and normalized label sources from runtime snapshot fields.

\subsection{Nightmare 12: floor-intro metadata rendered in incorrect contexts}
\textbf{What happened}: Floor/name overlays appeared at match start in contexts where they were inaccurate or noisy, reducing UX quality.

\textbf{Fix}: Removed incorrect floor-intro overlays and restricted progression messaging to valid events.

\subsection{Nightmare 13: asset memory pressure during long sessions}
\textbf{What happened}: Long sessions with multiple screen transitions increased texture/object retention risk, degrading performance on lower-end devices.

\textbf{Fix}: Tightened cleanup strategy for temporary graphics, animated sprites, and transition artifacts.

\section{Verification and Quality Assurance}

\subsection{Functional validation}
\begin{itemize}[leftmargin=6mm]
  \item calibration run correctly records keystrokes, tile movement, and zone dwell metrics;
  \item all eight search algorithms execute through the same registry and return comparable metrics;
  \item iteration completion writes proof records (strength deltas, algorithm distributions, fitness trends);
  \item analytics dashboard updates from live enemy snapshots during gameplay.
\end{itemize}

\subsection{Release validation checklist}
\begin{itemize}[leftmargin=6mm]
  \item no known critical runtime blockers in main gameplay loop;
  \item map select, character select, and game start transitions stable;
  \item allies and enemies move/attack reliably without lock-state regressions;
  \item report and phase documentation aligned with evaluator wording.
\end{itemize}

\section{Risk, Limitations, and Future Work}

\subsection{Current limitations}
\begin{itemize}[leftmargin=6mm]
  \item browser performance varies heavily by GPU/driver path and can affect smoothness;
  \item evolution quality depends on run diversity; short repetitive runs can bias adaptation;
  \item static-host operations rely on external env correctness for Supabase connectivity.
\end{itemize}

\subsection{Technical risks}
\begin{itemize}[leftmargin=6mm]
  \item adding new enemy archetypes can reintroduce mapping drift if naming contracts are not enforced;
  \item algorithm-level tweaks can unintentionally bias comparative analytics if output schema changes;
  \item additional visual assets may increase memory pressure and startup time.
\end{itemize}

\subsection{Recommended future work}
\begin{itemize}[leftmargin=6mm]
  \item formal benchmark harness for deterministic algorithm timing across map classes;
  \item stronger schema validation between enemy types, character defs, and analytics labels;
  \item CI pipeline step to compile LaTeX report and validate no broken references.
\end{itemize}

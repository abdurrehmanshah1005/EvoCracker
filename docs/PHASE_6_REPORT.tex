\begin{abstract}
EvoCracker is a browser-based roguelike dungeon crawler in which the player
descends through procedurally-generated floors contending against enemies
whose tactical behaviour is governed by \emph{genetically-evolved Behaviour
Trees} and one of eight classical search algorithms. Each run feeds player
strategy data into a genetic algorithm that evolves the enemy population for
subsequent iterations, creating a co-evolutionary loop that continuously adapts
enemy difficulty and playstyle diversity. This report presents the full technical
architecture: the core engine, the Entity–Component–System backbone, the
evolutionary AI pipeline, the algorithmic search layer, the rendering and
tilemap subsystems, the state-management and analytics infrastructure, and
the UI screens that tie them together.
\end{abstract}

\section{System Overview}
% ===========================================================================

EvoCracker is built as a single-page TypeScript application running on top of
PixiJS~v8 (WebGL/Canvas rendering) with React for UI overlays and Zustand for
centralised state management.  The codebase is organised into seven top-level
subsystems under \texttt{src/}:

\begin{enumerate}
  \item \textbf{Core} — engine primitives: EventBus, Camera, InputManager,
        SpriteFactory, AssetLoader, DungeonTilesetLoader, and the ECS
        scaffolding.
  \item \textbf{AI} — behaviour trees, genetic algorithm, and eight
        pathfinding / search algorithms.
  \item \textbf{Game} — entities, systems, world generation, tilemap rendering,
        and map loading.
  \item \textbf{Store} — Zustand store holding all mutable game state,
        including the evolutionary learning history.
  \item \textbf{UI} — React screens (MainMenu, GameScreen, AlgorithmLab, …),
        HUD overlays, and analytics dashboards.
  \item \textbf{Services} — Supabase client for leaderboards and cloud
        persistence.
  \item \textbf{Utils} — shared constants, math helpers, seeded random,
        and the priority queue.
\end{enumerate}

\section{Core Engine}
% ===========================================================================

The core layer provides the foundation on which all game logic runs.

\subsection{EventBus}
A singleton pub/sub dispatcher (Figure~\ref{fig:eventbus}).  Every
inter-subsystem notification flows through typed event channels (e.g.\,
\texttt{PLAYER\_MOVE}, \texttt{ENEMY\_DEATH}, \texttt{EVOLUTION\_COMPLETE}).

\subsection{Camera}
A 2-D camera with smooth lerp follow, deadzone, world clamping, and
screen$\leftrightarrow$world coordinate conversion.  Exposes
\texttt{getVisibleBounds()} for frustum culling.

\subsection{InputManager}
Robust singleton that tracks keyboard and mouse state per frame.
Provides \texttt{isKeyDown}, \texttt{isKeyJustPressed}, and
\texttt{getMovementVector()} helpers.  Handles tab-visibility and
window-blur resets to avoid stuck keys.

\subsection{SpriteFactory}
Loads 12 distinct character sprite sheets (Ghost, Heroine, Ogre, Knight,
WereWolf, Demon, Toad, Dragon, Lizzard, SpaceMarine, Froggy, Mushroom) and
creates \texttt{GameSprite} objects that wrap a PixiJS \texttt{Container}
with \texttt{setAnimation}, \texttt{setFlipX}, and \texttt{updateHealthBar}
methods.  Each sprite sheet is processed with automatic background-colour
removal and frame extraction.

\subsection{AssetLoader \& DungeonTilesetLoader}
The \texttt{AssetLoader} provides a centralised texture cache with probe-and-
fallback semantics.  \texttt{DungeonTilesetLoader} parses both legacy
(tileset\_v2.png) and Tiled-JSON–compatible tileset textures, including
multi-tileset GID resolution, animated tile support, and flip-flag stripping.

\section{Entity–Component–System Architecture}
% ===========================================================================

The game runtime is built on a custom ECS (Figure~\ref{fig:ecs}).

\subsection{Components}
Plain data objects attached to entities:
\begin{itemize}
  \item \texttt{PositionComponent} — grid $(c, r)$
  \item \texttt{MovementComponent} — smoothed pixel position, speed, target
  \item \texttt{HealthComponent} — current/max HP
  \item \texttt{RenderComponent} — PixiJS \texttt{GameSprite} wrapper
  \item \texttt{AIComponent} — algorithm selection, behaviour-tree state,
        genome reference, path-following state
  \item \texttt{PlayerComponent} — marker component for the player entity
  \item \texttt{CombatComponent} — damage, attack cooldown, range
\end{itemize}

\subsection{World (Entity Manager)}
The \texttt{World} class holds the entity pool and all component arrays
(typed dense arrays for cache-friendly iteration).  It provides
\texttt{createEntity}, \texttt{addComponent}, \texttt{removeComponent}, and
\texttt{query} (by component mask) methods.

\subsection{Systems}
Each system runs once per frame and operates on a filtered subset of entities:

\begin{center}
\begin{tabular}{>{\ttfamily}l>{\raggedright\arraybackslash}p{7cm}}
\toprule
\multicolumn{1}{c}{\textbf{System}} & \textbf{Responsibility} \\
\midrule
MovementSystem    & Lerps entity sprites toward grid targets; handles collision resolution against the tile grid. \\
RenderSystem      & Syncs PixiJS display objects with component state (position, animation, flip, health bar). \\
AISystem          & Runs behaviour-tree ticks, triggers pathfinding requests, and updates AI state machines. \\
CombatSystem      & Processes attack cooldowns, applies damage, and emits death events. \\
PlayerSystem      & Processes input, performs grid movement, and handles item usage. \\
FOVSystem         & Computes field-of-view per entity using shadowcasting; writes visibility maps for the renderer. \\
\bottomrule
\end{tabular}
\end{center}

\section{The Game Brain — Evolutionary AI Pipeline}
% ===========================================================================

The ``game brain'' is the centrepiece of EvoCracker.
It combines three AI layers that govern every enemy decision
(Figure~\ref{fig:gameBrain}):

\subsection{Behaviour Trees (BT)}
Each enemy is controlled by a genetically-parameterised Behaviour Tree.
The tree nodes include:

\begin{center}
\begin{tikzpicture}[
  level distance=12mm,
  level 1/.style={sibling distance=30mm},
  level 2/.style={sibling distance=22mm},
  level 3/.style={sibling distance=14mm},
  every node/.style={draw, rounded corners=2pt, font=\footnotesize,
                     minimum width=18mm, minimum height=6mm, align=center}
]
\node[fill=accentPurple!15] {Root: Selector}
  child { node[fill=accentGreen!12] {Combat\\Sequence}
    child { node[fill=green!8] {IsPlayerInRange?} }
    child { node[fill=red!12] {Attack} }
  }
  child { node[fill=accentOrange!12] {Chase\\Sequence}
    child { node[fill=orange!8] {DetectPlayer?} }
    child { node[fill=orange!8] {SetPathTarget} }
  }
  child { node[fill=accentBlue!12] {Patrol\\Sequence}
    child { node[fill=blue!8] {SelectPatrolPoint} }
    child { node[fill=blue!8] {FollowPath} }
  }
  ;
\end{tikzpicture}
\end{center}

The gene values (speed, visionRange, aggression, persistence, cautiousness,
packTendency, ambushTendency, patrolVariance) influence thresholds, cooldowns,
and probabilities inside the tree nodes, creating distinct enemy personalities.

\subsection{Search / Pathfinding Algorithms}
When an enemy needs a path, the BT invokes one of \textbf{eight} graph-search
algorithms implemented on the tile grid:

\begin{center}
\begin{tabular}{>{\ttfamily}l>{\raggedright\arraybackslash}p{4cm}c}
\toprule
\multicolumn{1}{c}{\textbf{Algorithm}} &
\multicolumn{1}{c}{\textbf{Type}} &
\multicolumn{1}{c}{\textbf{Key Property}} \\
\midrule
BFS           & Uninformed        & Shortest path (unweighted) \\
DFS           & Uninformed        & Deep exploration, non-optimal \\
IDS           & Uninformed        & Iterative deepening, memory-efficient \\
DLS           & Uninformed        & Depth-limited DFS \\
UCS           & Informed (cost)   & Optimal for weighted grids \\
A*            & Informed          & Optimal with heuristic \\
Greedy BFS    & Informed          & Fast, heuristic-driven, non-optimal \\
Hill Climbing & Local search      & Simple gradient ascent \\
\bottomrule
\end{tabular}
\end{center}

Each enemy is assigned one algorithm at spawn.  The algorithm determines how
the enemy finds paths to the player or patrol waypoints.
The \texttt{AlgorithmLabScreen} provides an interactive visualiser where all
eight algorithms can be compared side-by-side on the same grid.

\subsection{Genetic Algorithm (GA)}
After a player completes (or dies in) a dungeon run, the system executes a GA
generation:

\begin{enumerate}
  \item \textbf{Evaluation} — The \texttt{PlayerProfile} is updated from the
        run data (path coverage, damage taken, kills, items used, survival
        time, keystroke patterns).  This profile encodes the player's
        \emph{strategy fingerprint}.
  \item \textbf{Fitness scoring} — Each enemy genome is scored against the
        player profile using a multi-objective fitness function that rewards
        genomes whose behaviour posed the greatest challenge:
        \[
        f(g) = w_1 \cdot \text{damageDealt} + w_2 \cdot \text{detections}
              - w_3 \cdot \text{timeStuck} + w_4 \cdot \text{areaCovered}
        \]
  \item \textbf{Selection} — Tournament selection with elitism preserves the
        top-$k$ genomes.
  \item \textbf{Crossover} — Uniform crossover between parent pairs produces
        offspring genomes.
  \item \textbf{Mutation} — Gaussian perturbation applied to each gene with
        configurable rate and magnitude.
  \item \textbf{Replacement} — The new population replaces the previous
        generation; difficulty is adjusted by comparing the population's
        average fitness against thresholds.
\end{enumerate}

This loop creates a \textbf{co-evolutionary dynamic}: as the player improves,
the enemies adapt.  All GA metadata (generation number, gene distributions,
fitness curves, algorithm distributions) is recorded in
\texttt{IterationProofData} for visualisation.

\section{World Generation}
% ===========================================================================

\subsection{DungeonGenerator}
Procedurally generates tile grids using BSP (Binary Space Partitioning):

\begin{enumerate}
  \item Recursively split the map region into smaller rectangles.
  \item Carve rooms inside leaf partitions.
  \item Connect sibling rooms with L-shaped corridors.
  \item Place doors at corridor–room junctions.
  \item Distribute enemies and props (treasure chests, stairs) by tile type.
\end{enumerate}

The generated \texttt{DungeonData} includes the tile grid (typed as
\texttt{TileType}), room rectangles, corridor segments, and a collision
bitmask for fast pathfinding queries.

\subsection{TilemapRenderer}
Renders the tile grid with frustum culling (visible-bounds from Camera),
animated tile support (torches, chests, spear traps, trapdoors, gates),
and FOV fog-of-war overlay.  Supports both procedurally-generated floors
(legacy tileset) and Tiled-JSON map floors (multi-tileset GID resolution).

\subsection{MapLoader}
Parses Tiled \texttt{.json} map files exported from the Tiled editor.
Supports multiple tile layers, object layers (spawn points, chest locations),
and tileset references with firstgid offsets.

\section{State Management \& Analytics}
% ===========================================================================

\subsection{Zustand Store (\texttt{gameStore.ts})}
The Zustand store is the single source of truth.  Key slices:

\begin{itemize}
  \item \textbf{Screen routing} — \texttt{currentScreen} drives React routing.
  \item \textbf{Game state} — floor, biome, dungeon data, pause flag.
  \item \textbf{Player state} — health, score, items, selected character.
  \item \textbf{Evolution state} — generation, population (Genome[]),
        player profile, generation history, iteration proof history.
  \item \textbf{Analytics} — per-enemy runtime metrics streamed to the
        analytics dashboard.
  \item \textbf{Debug toggles} — FOV overlay, grid overlay, path rendering.
\end{itemize}

The store is \textbf{automatically persisted} to \texttt{localStorage} via
Zustand's \texttt{persist} middleware, allowing evolutionary progress to
survive page reloads.

\subsection{Enemy Analytics}
Every enemy emits real-time analytics (algorithm used, nodes expanded, path
length, compute time, damage dealt, detections, survival time, area covered)
via the \texttt{EventBus}.  These are aggregated in the store and visualised
in the \texttt{AnalyticsOverlay} with time-series charts, algorithm-distribution
pie charts, and per-enemy detail cards.

\subsection{Supabase Integration}
Leaderboard scores and player profiles are synchronised to a Supabase backend
via \texttt{SupabaseService}.  The schema (defined in
\texttt{SUPABASE\_SCHEMA.sql}) stores runs, genomes, and iteration proofs.

\section{Conclusion}
% ===========================================================================

EvoCracker demonstrates a cohesive integration of classical game-engine
architecture (ECS, tilemaps, sprite rendering) with modern evolutionary AI
techniques.  The three-layer Game Brain—Behaviour Trees parameterised by a
Genetic Algorithm, driving eight separable pathfinding strategies—creates
emergent enemy behaviour that adapts to individual player playstyles across
iterations.  The technical architecture is modular, event-driven, and
well-suited for continued research into co-evolutionary game AI.
